# harness-cli — Work Log (orchestrated)

Tracking implementation of 3 sequential OpenSpec changes (planned together, built one
at a time, single implementer — file overlap between changes is high enough that
parallel sub-agents would collide more than they'd help). Read the most recent entry
for current state.

## Plan

1. `add-rule-scoping-and-drift-detection` (17 tasks) — lowest risk, no shared infra.
2. `add-lifecycle-gating-and-parallel-orchestration` (24 tasks) — depends on nothing
   from (1), but is the biggest or riskiest of the three (new lock primitive + new
   advance.js gates).
3. `add-memory-compaction-symbol-index-and-guardian-judge` (17 tasks) — soft-depends on
   (1)'s `rulesForFile`/glob and (2)'s `withHarnessRCLock`/`diffFilesForSpec` for nicer
   integration, but each task explicitly degrades gracefully if those aren't present
   (see design.md "Decisions"), so order is not a hard blocker.

Each change: implement tasks in order → run `node tests/runner.js` (must stay green) →
`openspec validate <change>` still passing → commit → mark tasks.md checkboxes →
`openspec archive <change>` once merged into main and verified.

### [6] Solo implementer — self-review pass ("mejoralo aún más")
- User asked for a fresh improvement pass. Did a critical self-audit instead of
  inventing new features, and found 3 real issues:
  1. **Symbol index staleness bug**: `loadSymbolIndex` had NO fingerprint check
     (unlike `retrieval.js`'s BM25 `loadIndex`, which auto-rebuilds when the
     corpus changes) — a cached symbol index would go stale forever, silently
     contradicting the "harness_context should just work automatically"
     principle from entry [5]. Fixed: added `fingerprint(cwd)` +
     `getSymbolIndex(cwd, harnessDir)` to `symbolIndex.js` (mirrors
     retrieval.js's pattern exactly), rewired `context.js` and
     `memory.js`'s `symbolCmd` to use it. Verified with a real CLI smoke test:
     changed a source file between two `harness context --symbol=` calls, the
     second call saw the new function with zero manual reindex step.
  2. **Zero test coverage for `src/cli.js`'s routing** — every existing test
     called command functions directly, bypassing `runCLI()`'s switch/case
     entirely, despite that routing being rewritten twice this session (entry
     [4]'s gate/judge consolidation, entry [5]'s tool reduction). A typo'd case
     label would have shipped silently. Added 5 tests exercising `runCLI()`
     itself (gate approve/clarify, judge record, orchestrate claim, unknown
     command fallback).
  3. **help.js's MCP tool count went stale a SECOND time** — after entry [5]'s
     tool reduction (24→20), `help.js` briefly still said "24 tools" (missed it
     in that pass). Fixed the number, and — since this is now a repeat failure
     mode — added a regression-guard test that reads harness-mcp.js's source,
     counts actual `name: 'harness_...'` tool definitions, and asserts it
     matches the number embedded in help.js's output. This is the kind of test
     the project's own new default rules (honesty, verification) call for:
     don't just fix the symptom, prevent the class of bug from recurring silently.
- Tests: 74 → 82 (2 symbol-staleness tests, 5 CLI-dispatcher tests, 1

### [5] Solo implementer — MCP tool reduction: automatic vs human-decision tools
- User's follow-up complaint went deeper than command count: "hay comandos que
  no se deberian usar, el agente los deberia usar automaticamente" — some
  MCP tools are lookups a HUMAN won't remember to ask for by name; the agent
  should call them proactively as part of its own reasoning, not wait to be
  told. Example given: `harness_memory_search`.
- Verified the example was literally true: `harness_context --query=` already
  calls the exact same BM25 `search()` internally (tokenOptimizer.js's
  `getOnDemandContext`) — `harness_memory_search` was 100% redundant as an MCP
  tool, not just "confusing".
- Applied the same logic to find 3 more of "the same type": `harness_memory_symbol`
  (folded into `harness_context --symbol=`, added that flag + wiring to
  context.js/symbolIndex.js), `harness_rules_list` (redundant — rules are
  ALREADY in `harness_context`'s ALWAYS tier via AGENTS.md's synced rules
  section), `harness_clarify` (redundant — `harness_advance` already runs the
  clarify check internally and reports the result, so a separate pre-check
  call adds a step without adding information).
- Did NOT remove `harness_approve`: reasoned explicitly that approval must stay
  a deliberate, non-automatable human action — automating it away would defeat
  the entire point of an approval gate.
- MCP tools: 24 → 20. CLI commands for all 4 folded lookups remain untouched
  (`harness memory search/symbol`, `harness rules list`, `harness gate clarify`)
  — a human exploring the vault directly still has them; only the redundant
  MCP-tool exposure was removed.
- Rewrote AGENTS.md section 9 with an explicit RULE block instructing agents to
  call `harness_context` proactively at the start of any task, not wait for a
  human to ask — this is the actual fix for "the user won't remember to search":
  move the responsibility onto the agent's standing instructions, not the human.
- Verified via raw MCP JSON-RPC: `tools/list` returns 20; calling a removed
  tool name returns a clean `Unknown tool` error (not a crash); `harness_context`
  with both `query` and `symbol` params returns both in one bundle.
- Tests: 72 → 74 (2 new tests for `context --symbol=`, using a small
  console.log-capture helper since `context()` prints rather than returns).
- Updated README/AGENTS.md tool counts and command tables to match.
